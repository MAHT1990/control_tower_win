> 담당: plan_requirement_analyzer · 깊이: deep · 총 FR 45 / NFR 20 · 공통 카테고리 7
> 본 문서는 카테고리·ID·우선순위 체계(§0) → 한눈에 표(§1) → FR/NFR 상세(§2~§3) → 제약·가정·후속숙제(§4~§5) 순으로 Control Tower의 요구사항을 정형화한다.

## 0. 개요

### 0-1. 목적·범위

본 문서는 Control Tower의 제품 정의·로드맵 4레이어·도메인 모델·IPC 통합 계약을 기능 요구사항(FR)·비기능 요구사항(NFR)·제약들을 정리한다..

- **대상 제품**: Control Tower — 로컬에서 여러 Claude Code/PowerShell 세션을 앱이 직접 소유(ConPTY 임베드)하여, 의도별 세션 프로파일로 띄우고·IPC 채널로 협업시키며·프롬프트 자산까지 관제하는 **단일 파워유저용 AI 세션 관제탑**.
- **정체성**: 겉보기엔 터미널 앱이지만, 본질은 AI 세션 오케스트레이션이다.

### 0-2. ID·카테고리 체계

- **FR-###**: 기능 요구사항, 3자리 zero-pad. 본 문서가 발번·freeze한다.
- **NFR-###**: 비기능 요구사항, 3자리 zero-pad. 본 문서가 발번·freeze한다.
- **7 공통 카테고리(3자 대문자)**: 본 문서가 도메인(제품의 4개 역량 클러스터+도메인 모델)에서 파생해 **확정(FREEZE)**한다. FR과 하위 기능정의(FN, 05)가 **동일 코드셋을 공유**하여 FR↔FN 추적의 기반이 된다. 하위 agent(05·07·09)는 새 카테고리를 만들지 않고 참조만 한다. 각 코드는 영어 단어의 약칭이며 **원어** 열에 출처를 밝힌다.

### 0-3. 우선순위 정의 (MoSCoW)

| 등급 | 정의 | 판정 기준 |
|---|---|---|
| **Must** | v1이 가치를 내려면 반드시 있어야 함. 없으면 제품 정체성 붕괴 | 오케스트레이션 substrate·핵심 역량 클러스터의 필수 경로 |
| **Should** | 중요하나 없어도 v1 출시 가능. 초기 마일스톤 직후 우선 보강 | 품질·편의·관측 심화 |
| **Could** | 있으면 좋음. 여력/후속 마일스톤에서 | pane 분할·상태 복원 등 "후속"으로 명시한 항목 |

### 0-4. 표기 규칙

- **AC**(수용 기준, Acceptance Criteria): 각 FR이 "충족되었다"를 판정하는 관찰 가능 조건. `/`로 복수 조건 구분.
- **근거**: 제품 결정 배경·로드맵 레이어·도메인 모델을 출처로 표기(정형화 추적성).
- **[L0~L3]**: 로드맵 레이어.

### 0-5. 용어 정의 (백지 독자용 최초 정의)

| 용어 | 정의 |
|---|---|
| `ConPTY` (Windows Pseudo Console) | Windows 의사 콘솔 API — 앱이 하위 셸/프로세스의 터미널 입출력을 직접 소유한다. |
| `ClickOnce` (.NET 배포) | 게시본을 설치·자동 업데이트하는 Windows/.NET 배포 방식. |
| `as` (IPC 세션 식별자) | 세션의 IPC 정체성 키 — OS 프로세스↔채널 멤버십을 잇는 이름. |
| `airspace` (네이티브 호스팅 겹침 제약) | 네이티브로 그려지는 영역 위에 일반 UI를 겹쳐 그릴 수 없는 제약. |

## 2. 기능 요구사항(FR) 상세

> 이 절의 설명은 전문용어 대신 일상 용어로 쓴다. "무엇을 하는 기능인지"를 누구나 그림처럼 떠올릴 수 있게 하는 것이 목적이다. 식별자·우선순위·근거는 그대로 둔다.

### 2-1. TRM — 터미널 임베드·렌더·탭 [L0 substrate]

#### [FR-001] 앱-소유 pwsh ConPTY 세션 생성(spawn) — Must
프로그램이 직접 새 명령창(PowerShell)을 하나 열고, 그 창을 처음부터 끝까지 프로그램이 가진다. 밖에서 이미 떠 있던 창을 끌어다 쓰는 방식이 아니라, 오직 이 프로그램이 직접 연 창만 다룬다.
- AC: 새 세션을 요청하면 명령창이 함께 열린다 / 프로그램을 닫으면 프로그램이 연 창들도 함께 정리된다 / 프로그램을 켜기 전부터 떠 있던 창은 목록에도, 조작 대상에도 들어오지 않는다
- 근거: ConPTY 0순위 빌드 순서, 앱-소유 세션만 제어한다는 방침

#### [FR-002] ConPTY 입출력 파이프 바인딩 — Must
프로그램이 각 창의 "글을 넣는 통로"와 "창이 뱉는 출력을 받는 통로"를 붙잡는다. 넣는 통로는 화면이 예쁘게 그려지는지와 상관없이 먼저 확보해, 명령이나 지시를 일찍부터 창 안으로 밀어 넣을 수 있게 한다. 창이 내놓는 출력은 프로그램이 받아 챙긴다.
- AC: 창의 출력이 화면에 그려지고 프로그램이 그 내용을 받아둘 수 있다 / 프로그램이 아무 글이나 창에 밀어 넣으면 창의 입력줄에 그대로 들어간다 / 통로에 문제가 생기면 그 창은 '오류' 상태로 바뀐다
- 근거: ConPTY 0순위 빌드 순서(주입 경로를 렌더보다 먼저 확보)

#### [FR-003] VT/ANSI 렌더링 — 엔진 위임 — Must
창의 화면(색·글자·커서 움직임 같은 표시)을 그려내는 일은 프로그램이 직접 하지 않고, 검증된 바깥 터미널 부품에 통째로 맡긴다. 이 맡기는 지점은 딱 한 곳으로 모아 두어, 나중에 더 나은 부품으로 갈아끼우기 쉽게 한다.
- AC: 색·커서 이동·화면 지우기 같은 표시가 화면에 정확히 나타난다 / 그리기 부품에 닿는 지점이 한 곳으로 모여 있어 교체가 쉽다
- 근거: 터미널 렌더는 외부 엔진에 위임한다는 방침

#### [FR-004] 터미널 화면 렌더 (색·커서·스크롤백) — Must
창이 내보내는 내용을 실시간으로 화면에 그린다. 글자 색, 커서 위치, 그리고 지나간 출력을 위로 되짚어 볼 수 있는 스크롤(스크롤백)까지 보여준다.
- AC: 글자와 앞·뒷 배경색, 커서 위치가 화면에 정확히 표시된다 / 지나간 출력을 위로 스크롤해 다시 볼 수 있다 / 창의 새 출력이 실시간으로 갱신된다
- 근거: 터미널 렌더는 외부 엔진에 위임한다는 방침

#### [FR-005] alt-screen / TUI 렌더 — Should
어떤 프로그램은 화면을 통째로 바꿔 쓰는 "전체 화면 모드"를 쓴다(예: claude 코드 화면). 그런 전체 화면으로 들어가고 나오는 전환도 깨짐 없이 그려낸다. 이 역시 바깥 터미널 부품이 알아서 해준다.
- AC: 전체 화면 모드로 들어가고 나오는 전환이 정확하다 / claude 화면이 깨지지 않고 표시된다 / 화면이 크게 자주 바뀌어도 안정적이다
- 근거: 공식 WT 렌더러가 VT 전체를 담당한다는 방침

#### [FR-006] 터미널 탭 컨테이너 (탭>터미널 트리) — Must
여러 창을 탭으로 담아 두고 골라 본다. 탭 하나가 여러 개의 창을 품을 수 있고(한 탭 안에서 나누는 건 FR-008), 왼쪽에는 "탭(부모) 아래에 창(자식)"이 나뭇가지 모양으로 보인다. 탭을 고르면 그 탭에 속한 창들이 오른쪽에 나타난다.
- AC: 탭이 나뭇가지의 부모로, 그 안의 창들이 자식(PID)으로 표시된다 / 탭을 고르면 그 탭의 창들이 오른쪽에 활성화된다 / 항목을 닫으면 해당 창도 함께 종료된다(FR-015)
- 근거: 단일 pane에서 탭 컨테이너로 단계화한다는 방침

#### [FR-007] 터미널 리사이즈·뷰포트 스크롤백 — Should
창의 보이는 크기를 바꾸면 그 안의 내용도 새 크기에 맞춰 줄바꿈이 다시 정리되고, 지나간 출력은 마우스 휠이나 스크롤바로 되짚어 볼 수 있다.
- AC: 창이나 칸의 크기를 바꾸면 글자가 새 폭에 맞춰 다시 줄바꿈된다 / 마우스 휠·스크롤바로 예전 출력을 다시 본다
- 근거: 공식 WT 렌더러가 VT 전체를 담당한다는 방침(렌더 품질)

#### [FR-008] pane 분할 (탭 내 다중 터미널) — Should
**한 탭 안에서** 화면을 여러 칸으로 나눠, 그 탭에 속한 창 둘 이상을 동시에 본다. v1에서는 칸들이 알아서 고르게 나뉘는 방식으로 제공하고, 경계를 손으로 끌어 조정하는 건 FR-044에서 다룬다.
- AC: 한 탭의 여러 창이 나란한 칸으로 동시에 보인다 / 지금 쓰고 있는(포커스된) 칸이 강조된다 / 창을 더하거나 빼면 칸들이 자동으로 다시 배치된다
- 근거: 단일 pane에서 탭 컨테이너로 단계화한다는 방침

#### [FR-009] 임베드 터미널 키보드 입력 포커스 — Must
화면에 박힌 창을 클릭해 두고 타자를 치면, 그 글자가 그 창 안으로 그대로 전달된다.
- AC: 지금 활성인 창에 커서를 두면 키 입력이 그 창으로 전달된다 / Ctrl+C·방향키·Enter 같은 특수키도 창이 알아듣는 형태로 정확히 전달된다
- 근거: ConPTY 0순위 빌드 순서(세션 I/O 소유)

#### [FR-010] 터미널 텍스트 선택·클립보드 복사 — Should
창에 그려진 글자를 마우스로 끌어 선택해 복사한다.
- AC: 드래그로 원하는 범위를 선택한다 / 복사하면 (줄바꿈까지 반영한) 실제 문장이 클립보드에 담긴다 / 선택한 게 없을 때는 붙여넣기로 창에 글을 넣을 수 있다
- 근거: 터미널 UX 정합(도메인)

#### [FR-044] pane 위치·크기 조정 — Should
나뉜 칸(FR-008)들의 경계선을 마우스로 끌어 각 칸의 크기를 조정하고 배치를 바꾼다. 자동으로 나뉘던 것에 손으로 맞추는 조정을 더한 것이다.
- AC: 칸 사이 경계를 끌면 양옆 칸 크기가 함께 조정된다 / 너무 작게는 줄어들지 않도록 최소 크기를 지킨다 / 맞춰 둔 배치가 유지·복원된다
- 근거: 터미널 멀티플렉서 관성(NFR-015), FR-008 확장

#### [FR-045] 세션 pane 전환 단축키 (Ctrl+1…N) — Should
키보드에서 Ctrl과 숫자를 함께 누르면 그 순번의 창으로 바로 넘어간다.
- AC: Ctrl+1~Ctrl+9로 해당 순번 창이 활성·강조된다 / 창 개수보다 큰 번호는 무시된다 / 목록에서 고르는 것과 똑같이 맞물려 움직인다
- 근거: FR-017(세션 전환)·NFR-014(키보드 중심 ≤3 상호작용)

#### [FR-046] 탭·터미널 표시 이름 변경 — Should
탭이나 창에 붙는 "보이는 이름"을 사용자가 원하는 대로 바꾼다. 이건 세션끼리 통신할 때 서로를 부르는 이름(Session.as, FR-023)과는 별개로, 순전히 눈에 보이는 딱지일 뿐이다. 왼쪽 나뭇가지에서 더블클릭이나 F2로 바로 고치거나, 오른쪽 클릭 메뉴로 바꾼다.
- AC: 이름을 바꾸면 나뭇가지·칸·탭 딱지에 바로 반영된다 / 빈 이름은 받지 않고 이전 이름을 유지하며, 같은 이름이 겹쳐도 괜찮다(보이기용이라 유일할 필요 없음) / 바꾼 이름은 켜져 있는 동안만 유지되고 다시 켜면 사라진다
- 근거: 터미널 멀티플렉서 관성(NFR-015), FR-006(탭 컨테이너) 확장

### 2-2. SES — 세션 생성·소유·제어 [L1]

#### [FR-011] 프로파일 기반 세션 기동 — Must
미리 만들어 둔 "세션 설정표(프로파일)"를 골라 실제 세션을 띄운다. 이 설정표가 프로그램의 중심으로, 무엇을 어떻게 띄울지가 여기에 다 적혀 있다.
- AC: 설정표를 골라 세션을 만들면 그 안의 시작 명령·작업 폴더·claude 자동 실행·넣어줄 스킬·참여 채널이 그대로 적용된다 / 만들어진 세션은 자기가 어느 설정표에서 나왔는지 기억한다
- 근거: 세션 프로파일을 오케스트레이션 중심 도메인으로 삼는다는 방침, 도메인 모델

#### [FR-012] 초기 명령·작업디렉토리 자동 적용 — Must
세션을 띄울 때 설정표에 적힌 작업 폴더로 먼저 이동하고, 정해 둔 시작 명령들을 자동으로 실행한다.
- AC: 세션이 시작되면 지정한 작업 폴더에서 시작된다 / 시작 명령이 순서대로 자동 실행된다 / 정해 둔 게 없으면 기본값(홈 폴더/기본 셸)으로 시작한다
- 근거: 도메인 모델(SessionProfile)

#### [FR-013] claude 자동 실행 — Must
설정표에서 "claude 자동 실행"을 켜 두면, 세션이 시작되자마자 claude 코드가 알아서 함께 실행된다.
- AC: 켜 둔 세션은 시작 직후 claude 실행 명령이 자동으로 들어간다 / 꺼 둔 세션은 그냥 명령창 상태로 남는다 / 실행이 실패해도 세션은 살아 있고 그 사실이 표시된다
- 근거: 터미널 오케스트레이션 역량, 도메인 모델

#### [FR-014] 임의 세션에 커맨드 주입 — Must
목록에 있는 어느 세션이든 골라, 프로그램에서 명령이나 지시를 그 세션 안으로 밀어 넣는다.
- AC: 대상 세션을 고르고 명령을 넣으면 그 세션에서 실행된다 / 그 세션이 뭔가 하고 있는 중에도 넣을 수 있다 / 여러 세션에 각각 따로 넣을 수 있다
- 근거: IPC 주입은 트리거 프롬프트 전송 방식이라는 방침(주입 경로 재사용)

#### [FR-015] 세션 종료 / 강제 종료 — Must
세션을 얌전히 닫거나(끝내는 명령을 넣어), 말을 안 들으면 강제로 끊는다.
- AC: 종료를 요청하면 세션과 그 창, 프로세스가 함께 정리된다 / 응답 없는 세션은 강제로 끌 수 있다 / 종료된 세션은 목록/탭에서 사라지거나 '종료됨'으로 표시된다
- 근거: 앱-소유 세션만 다룬다는 방침(lifecycle도 앱이 정리)

#### [FR-016] 세션 런타임 상태 추적 (pid·as·상태) — Must
각 세션이 지금 어떤 상태인지 — 프로세스 번호, 통신용 이름, 그리고 시작 중인지·돌아가는 중인지·끝났는지·오류인지 — 를 계속 파악한다.
- AC: 세션마다 프로세스 번호·통신용 이름·상태(starting/running/exited/error)를 확인할 수 있다 / 프로세스가 끝나면 그 사실이 상태에 반영된다
- 근거: 도메인 모델(Session 런타임)

#### [FR-017] 다중 세션 목록·전환 관리 — Must
프로그램이 띄운 세션들을 한 목록으로 모아 관리하고, 지금 볼 세션을 바꾼다. 다루는 건 프로그램이 직접 띄운 세션으로만 한정한다.
- AC: 지금 프로그램이 가진 세션 전부가 목록에 보인다 / 목록과 탭(FR-006)이 서로 맞물려 움직인다 / 목록에서 고르면 그 세션으로 넘어간다
- 근거: 터미널 오케스트레이션 역량

#### [FR-018] 세션 재시작 (동일 프로파일 재기동) — Should
끝난 세션을 같은 설정표로 다시 띄운다.
- AC: 끝난 세션을 재시작하면 같은 설정표로 새 세션이 만들어진다 / 이전의 통신용 이름·채널 참여를 이어받는 선택지를 준다
- 근거: 도메인 모델(profile 재사용)

#### [FR-047] 터미널 간 출력 라우팅 (캡처 버퍼·가공·주입) — Should
한 세션(A)이 내놓은 출력을 프로그램 안 임시 보관함에 담아, 사용자가 보고 다듬은 뒤, 다른 세션(B나 여럿)의 입력으로 밀어 넣는다. 즉 A의 출력을 받아(FR-002) B로 넣는(FR-014) 두 능력을 이어, 세션끼리 결과를 주고받게 하는 것이다. 채널 파일을 통한 통신(FR-024)과는 별개로, 화면에 나온 날것의 출력을 직접 나르는 길이다. 기존의 손복사(FR-010)를 프로그램 안 보관함·다듬기·여러 곳 넣기로 끌어올린 것이다.
- AC: A의 출력(선택분/방금 명령/흐름)을 보관함에 담는다 / 보관함 내용을 보고 고칠 수 있다 / 넣을 세션(하나 또는 여럿)을 골라 넣는다(어디로 넣는지 명시, 위험하면 확인 단계 FR-037을 거침) / 여러 곳에 각각 따로 넣는다 / 보관함은 켜져 있는 동안만 유지된다
- 근거: 제품 정체성(세션 간 오케스트레이션), FR-002·FR-014 기반

### 2-3. PRF — 세션 프로파일 [L1]

#### [FR-019] 세션 프로파일 생성·편집 — Must
세션 설정표의 항목들 — 용도 태그, 시작 명령, 작업 폴더, 넣어줄 스킬 목록, 참여할 채널 목록, claude 자동 실행 여부 — 를 만들고 고친다. 용도 태그는 목록에서 이 설정표를 부르는 이름도 겸한다.
- AC: 여섯 항목을 모두 고칠 수 있다 / 꼭 필요한 항목은 유효한지 확인한다(작업 폴더가 실제로 있는지 등) / 저장하면 다시 쓸 수 있는 설정표로 등록된다
- 근거: 세션 프로파일을 오케스트레이션 중심 도메인으로 삼는다는 방침, 도메인 모델

#### [FR-020] 세션 프로파일 영속화·목록·재사용 — Must
설정표를 저장해 목록으로 모아 두고 두고두고 다시 쓴다. 저장 형식(파일이냐 DB냐)은 뒤에서 정한다.
- AC: 프로그램을 껐다 켜도 설정표 목록이 그대로 남아 있다 / 설정표를 골라 세션을 띄운다(FR-011) / 저장은 중간에 끊겨도 안 깨지게 한 번에 이뤄진다(NFR-011)
- 근거: 세션 프로파일은 저장·재사용 가능해야 한다는 도메인 모델 방침, 오픈이슈(영속화 형태)

#### [FR-021] 세션 프로파일 복제·삭제 — Should
이미 있는 설정표를 복사해 조금 바꿔 쓰거나, 지운다.
- AC: 복사하면 항목을 물려받은 새 설정표가 생긴다(통신용 이름은 새로) / 지우면 목록에서 빠지고, 이미 돌아가는 세션에는 영향이 없다
- 근거: 세션 프로파일 관리 도메인

#### [FR-022] 의도별 프로파일 프리셋 — Should
control, sangmin+noter, Proj_N 처럼 자주 쓰는 용도별 묶음을 미리 만들어 두고 바로 꺼내 쓴다.
- AC: 용도 태그별로 설정표를 묶거나 걸러 본다 / 자주 쓰는 조합을 미리 만들어 두고 바로 띄운다
- 근거: 터미널 오케스트레이션 역량(의도별 세션)

#### [FR-023] Session.as (IPC 식별자) 정의 — Must
설정표에 세션의 "통신용 이름"(예: tower2, sangmin-noter)을 정한다. 이 이름은 세션끼리 대화(채널 통신)할 때 서로를 부르는 정체성 키다.
- AC: 설정표에 통신용 이름을 정하고 확인한다(한 채널 안에서는 겹치지 않도록 권함) / 세션을 띄우면 이 이름이 세션에 따라붙는다(FR-016) / 채널로 주고받고 참여하는 일(FR-025~026)이 이 이름을 쓴다
- 근거: 도메인 모델(Session.as = IPC 식별자)

### 2-4. IPC — 채널·협업·주입 [L2]

#### [FR-024] IPC 채널 상태 관측 (파일 watch/read) — Must
이 프로그램은 세션 간 통신 스킬(skill_ipc_control)의 앞단 화면 역할이다. 통신이 오가는 채널 폴더 안의 파일들(주고받은 메시지 기록 등)을 직접 들여다보고 변화를 지켜본다. 통신 기능 자체를 새로 만들지 않는다.
- AC: 채널의 메시지 기록이 바뀌면 화면에 반영된다 / 채널이 있는지·누가 듣고 있는지 등을 확인할 수 있다 / 통신 로직을 새로 짜지 않고 기존 파일 약속만 읽어 쓴다
- 근거: skill_ipc_control의 GUI 프론트엔드라는 방침

#### [FR-025] 채널 메시지 송신 (send.cmd 재사용) — Must
세션끼리 대화하도록 이미 있는 보내기 도구(send.cmd)를 그대로 써서 메시지를 보낸다. 통신 장치를 새로 만들지 않고 재사용한다.
- AC: 보내는 이·받는 이·내용을 넣으면 기존 보내기 도구로 메시지가 기록에 남는다 / 받는 이 표기(한 명/전원/여러 명)를 지원한다 / 보낸 결과(메시지 번호·시각)를 보여준다
- 근거: skill_ipc_control의 GUI 프론트엔드라는 방침, skill_ipc_control 계약

#### [FR-026] 세션-채널 멤버십 관리 — Must
세션(통신용 이름)이 어느 대화 채널에 들고 나는지를 관리한다. 설정표의 참여 채널 목록과 실제 세션을 이어 준다.
- AC: 세션을 채널에 참여시킨다 / 채널 참여자 목록에 그 세션 이름이 나타난다 / 설정표에 적힌 참여 채널이 세션을 띄울 때 적용된다(FR-011)
- 근거: 도메인 모델(Channel.members ↔ SessionProfile.채널멤버십)

#### [FR-027] IPC 스킬 주입 (트리거 프롬프트 전송) — Must
아직 통신 준비가 안 된 세션에게 "통신 시작해" 하는 지시문을 그 세션 안으로 밀어 넣어, 세션이 스스로 통신 스킬을 켜게 한다. 한 컴퓨터 안에서는 스킬 파일이 공유되므로 따로 파일을 심을 필요가 없다.
- AC: 대상 세션을 고르면 통신 시작 지시문이 그 세션에 들어간다(FR-014 길 재사용) / 설정표의 넣어줄 스킬 목록을 바탕으로 지시문이 꾸려진다 / 세션이 스킬을 켠 뒤 채널로 주고받을 수 있다
- 근거: IPC 주입은 트리거 프롬프트 전송 방식이라는 방침

#### [FR-028] 채널 대화 뷰 (메시지 시각화) — Should
채널에서 오간 메시지를 대화(채팅)처럼 보여준다. 기존 채널 시각화 웹앱(web_monitor)을 흡수할지 따로 둘지는 뒤에서 정한다.
- AC: 채널을 고르면 메시지가 시간순 대화로 보인다 / 보낸 이·받는 이·내용이 구분되어 보인다 / 새 메시지가 실시간으로 이어 붙는다
- 근거: web_monitor(채널 시각화)와의 관계 정리(오픈이슈)

#### [FR-029] 앱 채널 ↔ skill_ipc_control channel 1:1 매핑 — Must
프로그램이 보여 주는 "채널" 하나가 통신 스킬의 채널 폴더 하나와 정확히 일대일로 맞물리게 한다.
- AC: 프로그램의 채널 이름이 실제 채널 폴더와 하나씩 짝지어진다 / 짝짓는 규칙이 정해져 주고받기·들여다보기가 일관된다 / (정해지기 전에는) 잠정 가정으로 동작한다
- 근거: 앱 Channel ↔ IPC channel 매핑 확정(오픈이슈)

### 2-5. AST — 프롬프트 자산 편집 [L3]

#### [FR-033] ~/.claude 자산 파일 트리 브라우저 — Must
프롬프트 자산이 담긴 폴더(~/.claude 아래 rules·skills·agents)를 나뭇가지 모양으로 훑어본다.
- AC: rules·skills·agents 아래 폴더와 파일이 나뭇가지로 보인다 / 훑어보고 고를 수 있다 / 다루는 범위는 ~/.claude 안으로만 제한된다(SEC, NFR-008)
- 근거: 기본 가정(프롬프트 편집 v1 범위), 프롬프트 자산 관리 역량

#### [FR-034] 자산 파일 읽기 (에디터 표시) — Must
고른 자산 파일의 내용을 편집기 화면에 펼쳐 보여준다.
- AC: 텍스트·마크다운 파일 내용이 편집기에 열린다 / 큰 파일도 열어 볼 수 있다
- 근거: 기본 가정(v1은 읽기까지)

#### [FR-035] 자산 파일 쓰기·저장 — Must
편집기에서 고친 내용을 파일로 저장한다. v1에서는 읽고 쓰는 데까지만 하고, 내용이 규칙에 맞는지 따지는 검사는 뒤로 미룬다.
- AC: 고친 내용이 중간에 안 깨지게 한 번에 저장된다(NFR-011) / 저장 성공·실패를 알려준다 / 형식 검사는 v1 범위 밖(후속)
- 근거: 기본 가정(v1은 쓰기까지), 오픈이슈(검증 후속)

#### [FR-036] 자산 파일 생성·삭제·이름변경 — Should
자산 나뭇가지에서 파일이나 폴더를 새로 만들고, 지우고, 이름을 바꾼다.
- AC: 새 rule·skill·agent 파일을 만든다 / 지우거나 이름 바꾸면 나뭇가지가 갱신된다 / 지우기 같은 위험한 작업은 확인을 받는다
- 근거: 오픈이슈(편집 v1 범위)

### 2-6. SEC — 보안·안전 [횡단]

#### [FR-037] 위험 커맨드 주입 확인 가드 — Should
지우기 같은 위험한 명령을 세션에 밀어 넣기(FR-014·027) 전에, 정말 할 건지 한 번 확인을 받는다.
- AC: 위험한 낌새의 명령(예: `rm -rf`, 대량 삭제)을 넣으려 하면 확인 창이 뜬다 / 사용자가 승인해야만 보내진다 / 어디까지를 위험으로 볼지는 뒤에서 정한다
- 근거: 안전(단일 파워유저이나 다중 세션 오조작 방지)

#### [FR-038] 로컬 전용·외부 비노출 정책 — Must
이 프로그램은 내 컴퓨터 안에서만 돈다. 바깥에서 접속해 들어올 수 있는 문(네트워크 포트)을 열지 않는다. 여러 기기를 넘나드는 원격 기능은 다음 버전(v2) 몫이다.
- AC: 프로그램이 외부에서 들어올 수 있는 문을 열지 않는다(NFR-006) / 통신은 내 컴퓨터 안 파일로만 이뤄진다 / 바깥으로 나가는 중계는 v2로 미뤄 꺼 둔다
- 근거: 기본 가정(로컬 전용), v1 범위는 로컬 전체·멀티디바이스만 v2라는 방침

#### [FR-039] 앱-소유 세션 범위 강제 — Must
다루고·밀어 넣고·지켜보는 대상은 오직 이 프로그램이 직접 띄운 세션뿐이다. 컴퓨터 전체의 아무 프로세스나 넘보지 않는다.
- AC: 프로그램 밖의 프로세스는 목록에도, 명령 넣는 대상에도 들어오지 않는다 / 모든 조작은 프로그램이 가진 세션에만 통한다
- 근거: 앱-소유 세션만 다룬다는 방침

### 2-7. SYS — 앱 셸·배포·플랫폼 [횡단]

#### [FR-040] 앱 셸 레이아웃·영역 조합 — Must
프로그램 전체 틀이 세션 탭·세션/설정표 목록·통신 채널·관측·자산 편집 같은 화면들을 자리에 배치해 하나로 엮는다.
- AC: 전체 틀에 주요 화면(터미널/세션/채널/관측/자산)이 자리 잡는다 / 전체 틀은 얇게, 배치만 맡고 실제 일은 각 기능이 한다 / 새 기능은 기능 단위로 덧붙인다
- 근거: Feature×Layer 모듈 구조(상세는 10)

#### [FR-041] ClickOnce 배포·자동 업데이트 — Must
프로그램을 ClickOnce 방식으로 설치·자동 업데이트한다.
- AC: ClickOnce로 설치·실행된다 / 새 버전을 올리면 자동으로 갱신된다
- 근거: 기본 가정(기존 배포 파이프라인 계승)

#### [FR-042] 앱 설정 관리 — Should
프로그램이 쓰는 주요 경로(~/.claude·채널 폴더 위치), 기본 설정표, 위험 명령 목록 같은 프로그램 설정을 관리한다.
- AC: 주요 경로·기본값을 정하는 설정 화면이 있다 / 설정이 저장된다 / 다시 켜도 반영된다
- 근거: 오픈이슈 연동(경로·범위 설정 필요)

#### [FR-043] 세션/프로파일 상태 앱 재시작 후 복원 — Could
마지막으로 열어 둔 구성(어떤 설정표·탭을 열고 있었는지)을 프로그램을 다시 켰을 때 되살린다. (세션 자체는 프로세스라 그대로 살릴 수 없어, 같은 설정표로 다시 띄우자고 제안하는 형태다.)
- AC(후속): 마지막 탭·설정표 구성을 저장한다 / 다시 켜면 같은 설정표로 다시 띄우자고 제안한다(FR-018 활용)
- 근거: 도메인 모델(profile 재사용)

#### [FR-048] 임베드 터미널 글꼴 설정 — Should
프로그램 전체 설정에서 터미널 글꼴을 바꾼다: ① 글자 크기(6~72 사이 자유롭게) ② 글자 종류(고정폭 글꼴 목록에서 고름, 기본은 Cascadia Code). 바꾸면 모든 터미널에 똑같이 적용된다(세션별·터미널별 따로 지정은 v1 제외, 후속 여지). 바꾼 값은 설정 파일에 안전하게 저장되어 다시 켜도 유지되고, 저장하는 즉시 켜져 있는 모든 터미널에 바로 반영되며 새로 여는 터미널에도 적용된다. 줄 간격·글자 사이 간격은 지금 쓰는 터미널 부품이 지원하지 않아(부품 확인 결과) v1에서는 빼고 뒤로 미룬다(숙제 ⑨). 글자·배경 색 테마는 범위 밖이다.
- AC: 글자 크기(6~72 자유 입력, 벗어나면 거부)·글자 종류(고정폭 목록에서 고름)를 설정 화면에서 바꾼다 / 설정 파일에 안전하게 저장되고 다시 켜도 유지된다(NFR-011) / 저장 즉시 켜진 모든 터미널에 바로 반영된다(엔진 경계 격리 NFR-013·018) / 새 터미널에도 같은 글꼴이 적용된다 / 줄 간격·글자 간격은 부품 미지원이라 v1에서 안 보인다(후속 ⑨) / 색 테마는 범위 밖
- 근거: 터미널 표시 옵션(글꼴) 커스터마이즈 도메인 UX · FR-042(설정 인프라) 보완 · 터미널 UX 정합(NFR-015) · 엔진 경계 무중단 반영(NFR-013)

## 3. 비기능 요구사항(NFR) 상세

> 측정 지표 값은 잠정 목표(가정)이며 §5 후속 숙제 ③(렌더 성능)·기술 스펙(10)에서 확정한다.

### 3-1. 성능 (Performance)

#### [NFR-001] 터미널 렌더 처리량 — Must
- 지표: 대량 출력(예: `cat` 대용량, 빌드 로그) 스트리밍 시 UI 프레임 유지 ≥ 30fps / 스크롤 리페인트 지연 ≤ 50ms
- 관련: FR-004·FR-005·FR-007 · 관련 숙제 ③
- 검증: 10만 라인 출력 스트레스에서 프레임 드랍/멈춤 없음(기술 스펙 PoC)

#### [NFR-002] 커맨드 주입 지연 — Must
- 지표: 커맨드 전송 요청→PTY write 반영 ≤ 100ms (로컬)
- 관련: FR-014·FR-027

#### [NFR-003] 다중 세션 동시성 — Should
- 지표: 8개 세션 동시 running 시 idle 앱 CPU ≤ 10%, 메모리 ≤ 800MB (기준 하드웨어)
- 관련: FR-017 · NFR-012

#### [NFR-004] IPC watch 반영 지연 — Should
- 지표: 채널 inbox.log 파일 변경→앱 UI 반영 ≤ 2s (파일 기반 watch, f_relay 폴링 기본 2s와 정합)
- 관련: FR-024·FR-028

### 3-2. 보안·안전 (Security/Safety)

#### [NFR-006] 로컬 전용·외부 포트 미개방 — Must
- 지표: 앱이 여는 수신 소켓/포트 = 0 (relay 서버는 앱 외부, v2)
- 관련: FR-038

#### [NFR-007] 파괴적 명령 실행 전 확인 — Should
- 지표: 정의된 위험 패턴 주입 시 100% 확인 게이트 경유
- 관련: FR-037 · 관련 숙제 ⑧

#### [NFR-008] 자산 편집 경로 안전 — Must
- 지표: 자산 편집 대상 경로가 `~/.claude` 밖으로 벗어나는 접근 0(경로 탈출 `..` 차단)
- 관련: FR-033~036

### 3-3. 가용성·신뢰성 (Availability/Reliability)

#### [NFR-009] 세션 크래시 격리 — Must
- 지표: 1개 세션/PTY 비정상 종료가 앱·타 세션에 전파되지 않음(격리 100%)
- 관련: FR-015·FR-016

#### [NFR-010] watcher/relay stale 복구 — Should
- 지표: stale `.watcher_<as>.pid` 감지 시 skill_ipc_control 가드와 정합되게 복구(자동 흡수), 사용자 동의 정책 준수
- 관련: FR-024 · skill_ipc_control Error Handling

#### [NFR-011] 상태 영속 원자성 — Must
- 지표: 프로파일/자산 저장 시 부분 기록으로 인한 손상 0 (원자적 write, temp→rename)
- 관련: FR-020·FR-035·FR-048 · 관련 숙제 ①

### 3-4. 확장성 (Scalability)

#### [NFR-012] 동시 세션 수 확장 — Should
- 지표: v1 목표 동시 세션 ≥ 8 (설계상 상한 아님), 목록/탭이 세션 수 증가에 선형 열화 이내
- 관련: FR-017

#### [NFR-013] 터미널 렌더 확장 무중단 — Should
- 지표: 렌더 기능 확장이 엔진 경계 격리 덕에 상위 오케스트레이션 재작업 없이 가능
- 관련: FR-004·FR-005·FR-048 · NFR-018

### 3-5. 사용성 (Usability)

#### [NFR-014] 단일 파워유저 워크플로 효율 — Should
- 지표: 핵심 동작(세션 기동·커맨드 주입·채널 송신)이 ≤ 3 상호작용, 키보드 중심 조작 지원
- 관련: FR-011·FR-014·FR-025

#### [NFR-015] 터미널 UX 정합 — Should
- 지표: 기본 상호작용(포커스 타이핑·복사·스크롤백)이 Windows Terminal/VS Code 터미널 수준 관성 유지
- 관련: FR-009·FR-010·FR-007

### 3-6. 유지보수성 (Maintainability)

#### [NFR-016] Feature × Layer 구조 준수 — Must
- 지표: 신규 기능이 모듈 경계(Feature×Layer)를 준수하고 Feature 간 직접 참조 0(결합 최소)
- 관련: FR-040

#### [NFR-017] IPC 재구현 금지 (계약 준수) — Must
- 지표: 앱이 IPC 전송/큐/watcher 로직을 재구현하지 않고 skill_ipc_control 스크립트/파일 계약만 소비(재구현 0)
- 관련: FR-024·FR-025

#### [NFR-018] 터미널 엔진 교체 가능성 — Should
- 지표: 엔진 경계 1곳으로 격리되어 엔진↔폴백 교체 시 상위 소비자 코드 변경 최소
- 관련: FR-003·FR-004

### 3-7. 호환성 (Compatibility)

#### [NFR-019] 플랫폼 호환 — Must
- 지표: Windows(11 기준)·.NET 10·WPF·ConPTY(`CreatePseudoConsole`) 환경에서 동작
- 관련: FR-001~002

#### [NFR-021] ClickOnce 배포 호환 — Should
- 지표: ClickOnce 게시 파이프라인과 호환
- 관련: FR-041

### 3-8. 관측성 (Observability)

#### [NFR-022] 앱 자체 진단 로그 — Should
- 지표: 세션 기동/종료·주입·IPC·엔진 오류가 앱 로그에 기록되어 사후 진단 가능
- 관련: FR-016·FR-024
